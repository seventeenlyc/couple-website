# Couple Website 当前项目完善设计文档

## 1. 设计目的

本文档把《当前项目完善需求文档》落实到现有代码。改造以当前已部署网站为基础，保留 HTML 页面、PHP API 和 JSON 数据文件，先解决稳定性、安全、移动端体验、数据一致性和维护问题。

本阶段采用渐进式改造：每一步都应保持网站可运行、现有数据可迁移、出现问题可回退。不会为了追求架构形式而一次性重写全部页面或替换存储方式。

## 2. 当前代码基线

项目现有结构已经覆盖完整的双人使用流程，但代码检查发现以下问题需要优先处理：

1. `data/config.json.example` 使用 `site.start_date`，`includes/config.php` 实际读取 `startDate`，存在配置含义不一致。
2. 页面中有部分上传和提交直接使用 `fetch` 或 `XMLHttpRequest`，没有完整经过公共 API 客户端。
3. CSRF、请求方法和错误输出已在部分接口实现，但写法分散，容易遗漏。
4. JSON 写入使用临时文件替换，但“读取、修改、写回”没有被同一文件锁完整包围，并发时可能丢失更新。
5. 签到、任务奖励、购买等操作可能同时修改多个数据文件，需要明确的一致性和回滚机制。
6. 多个页面通过模板字符串写入 `innerHTML`，需要确认所有动态字段都经过转义。
7. 大量页面逻辑仍写在 HTML 内部，重复的加载、提示、弹窗和上传逻辑难以统一维护。
8. 当前自动化测试主要集中在相册文件夹和标签，其他关键流程缺少保护。
9. README 仍使用 PHP 7.4 和 `chmod 777` 示例，与目标部署要求不一致。
10. 所有页面运行时依赖 Tailwind CDN、Google Fonts 和外部 Font Awesome，登录页还有外部装饰图片；外部资源不可用时会影响样式、图标和加载速度。

## 3. 总体架构

改造后的请求路径如下：

```text
浏览器页面
  -> 公共前端模块（请求、状态、弹窗、上传）
  -> PHP API
  -> bootstrap（会话、响应头、错误处理、请求 ID）
  -> 请求与权限校验
  -> 业务 helper
  -> JSON 数据访问层（锁、校验、原子写入、备份）
  -> data/ 与 uploads/
```

各层职责：

| 层级 | 职责 | 约束 |
| --- | --- | --- |
| 页面层 | 展示和交互 | 不拼接未转义的用户数据，不自行实现鉴权规则 |
| 前端公共层 | API、上传、状态、弹窗 | 统一处理 401、403、网络错误、重复提交和请求 ID |
| API 层 | 路由和协议 | 只解析请求、校验权限、调用业务函数、返回统一响应 |
| 业务层 | 任务、积分、相册、小铺等规则 | 不直接输出 HTTP 内容 |
| 数据层 | JSON 读写与文件事务 | 所有修改在锁内完成，失败可恢复 |
| 文件层 | 图片与私密文件 | 路径受控、随机文件名、受控访问 |

## 4. 统一约定

### 4.1 PHP 约定

1. 最低目标版本为 PHP 8.2。
2. 新增代码使用严格类型、返回类型和明确异常。
3. 所有 API 第一行加载 `includes/bootstrap.php`。
4. API 不直接散落调用 `header()`、`echo json_encode()` 和 `exit`，统一使用响应函数。
5. 业务错误使用稳定错误码，日志使用请求 ID 关联。

### 4.2 API 响应

成功响应：

```json
{
  "success": true,
  "data": {},
  "message": "操作成功",
  "request_id": "随机请求标识"
}
```

失败响应：

```json
{
  "success": false,
  "error_code": "INVALID_INPUT",
  "message": "请输入有效内容",
  "request_id": "随机请求标识"
}
```

状态码使用规则：

| 状态码 | 使用场景 |
| --- | --- |
| 200 | 查询成功、幂等重复请求已得到既有结果 |
| 201 | 新资源创建成功 |
| 400 | 请求格式或字段错误 |
| 401 | 未登录或会话过期 |
| 403 | CSRF、私密空间验证或操作权限失败 |
| 404 | 资源不存在 |
| 409 | 状态冲突或重复操作 |
| 413 | 请求或文件过大 |
| 422 | 字段格式正确但业务规则不允许 |
| 429 | 请求过于频繁 |
| 500 | 未预期服务端错误 |

### 4.3 配置规范

新的规范字段使用：

```json
{
  "site": {
    "name": "我们的小窝",
    "description": "情侣专属网站",
    "start_date": "2025-02-05",
    "timezone": "Asia/Shanghai"
  }
}
```

读取顺序：

1. 优先读取 `site.start_date`。
2. 若不存在，兼容读取旧 `startDate`。
3. 两者都不存在时视为配置错误，不静默使用代码中的固定日期。

密码字段升级时保留兼容读取，但启动检查应提示仍在使用明文的字段，并提供命令生成哈希。AI 密钥优先读取环境变量 `AI_API_KEY`，配置文件只保留无密钥的功能选项。

七个页面共同移除运行时 Tailwind CDN、Google Fonts 和外部 Font Awesome 依赖。开发阶段生成实际用到的静态 CSS，字体和图标使用固定版本的站内资源；构建产物随代码部署，服务器运行时不需要 Node.js。

## 9. API 文件逐项改造

所有接口共同执行：加载 `bootstrap.php`、限制方法、验证输入、验证登录与 CSRF、调用业务函数、返回统一结构、记录异常请求 ID。

| 文件 | 需要修改 |
| --- | --- |
| `api/ping.php` | 只返回登录状态和必要健康信息；不暴露路径、PHP 小版本或配置内容 |
| `api/csrf-token.php` | 生成与当前会话绑定的令牌；设置禁止缓存；不把未登录状态误判为异常 |
| `api/login.php` | 仅 POST；统一读取表单；按账号与来源组合限制；成功后轮换会话；支持安全的返回地址 |
| `api/logout.php` | 改为 POST + CSRF；清空主会话、私密会话和 Cookie；重复退出保持幂等 |
| `api/app-config.php` | 只返回前端需要的站点名、日期、主题、成员显示信息和功能开关；不返回密码、私密密码、密钥或服务器路径 |
| `api/anniversary-reminders.php` | 使用规范日期与时区；限制查询范围；单条生日配置错误时记录并跳过 |
| `api/daily-quote.php` | 要求登录；设置 AI 超时；按日期缓存；写历史使用锁；服务失败时返回本地文案和回退标识 |
| `api/upload-avatar.php` | 使用公共上传模块；验证 CSRF、MIME、像素和大小；GD 重编码；原子更新头像配置；失败时清理临时文件 |
| `api/upload-photo.php` | 使用公共上传模块；严格验证文件夹路径与标签；先生成文件和缩略图，再在锁内写相册数据；任一步失败执行清理 |
| `api/photos.php` | GET 列表支持文件夹和分页；删除只接受 POST；数据记录与磁盘文件按明确顺序更新并可补偿失败 |

| `api/shop.php` | 查询与购买分离；购买校验快照中的商品价格、库存和余额；使用幂等键与跨文件事务 |
| `api/orders.php` | 只返回当前成员有权查看的订单；分页和排序参数白名单；状态更新必须校验合法转换 |

上传顺序：

1. PHP 接收文件到系统临时目录。
2. 检查上传错误、大小、MIME 和图片像素。
3. 生成随机目标名，在应用临时目录用 GD 重编码。
4. 生成并验证缩略图。
5. 原子移动到最终目录。
6. 在数据锁内添加元数据。
7. 元数据失败时删除本次新建文件；清理失败则记录待清理任务。

## 13. 关键业务事务

### 13.1 单文件更新

`atomicUpdateJSON(path, validator, mutator)` 执行：

1. 打开对应锁文件并取得独占锁。
2. 重新读取当前主文件。
3. 校验旧数据。
4. 调用业务修改函数得到新数据。
5. 校验新数据并写入随机临时文件。
6. 刷盘、替换主文件、更新可用备份。
7. 释放锁并返回最终结果。

锁必须覆盖整个读改写过程，不能只在 `file_put_contents` 时加锁。

### 13.2 跨文件更新

签到、任务确认和购买使用一个固定的事务锁，避免不同请求以不同顺序锁文件造成死锁。事务开始后保存相关文件快照，所有新数据先写临时文件，全部验证通过后依次替换。提交中途失败时从快照恢复，并记录高优先级日志。

### 13.3 幂等处理

签到以用户和日期作为自然幂等键。任务确认以任务 ID 和目标状态作为幂等边界。购买由前端生成一次性请求键，服务端将其记录到订单；重复请求直接返回原订单。

## 14. 安全设计

### 14.1 启动与响应头

`bootstrap.php` 在任何业务输出前设置：

- `Content-Security-Policy`：只允许本站资源和明确列出的外部字体或样式来源。
- `X-Content-Type-Options: nosniff`。
- `Referrer-Policy: same-origin`。
- `X-Frame-Options: DENY` 或等价 CSP。
- API 响应使用 `Cache-Control: no-store`，静态图片使用单独缓存策略。

生产环境关闭页面错误展示，异常写入结构化日志。错误响应只提供错误码、可理解信息和请求 ID。

### 14.2 CSRF

令牌和会话绑定，前端公共客户端自动附加。JSON 写入放在请求体，文件上传放在表单字段，退出同样使用 POST。服务端不根据是否“看起来像 AJAX”放宽验证。

### 14.3 XSS

动态内容分为纯文本、受控 URL 和受控枚举三类。悄悄话、笔记、任务、评价、事件和标签都作为纯文本。图片 URL 只能是服务端返回的站内相对路径。颜色、图标名和状态必须通过白名单。

### 14.4 私密文件

私密文件列表只返回记录 ID、展示名、大小、类型和时间。下载请求使用记录 ID，服务端完成主会话、私密会话和路径校验后，通过 `Content-Disposition: attachment` 输出，不返回磁盘位置。

## 15. 前端交互设计

### 15.1 公共状态组件

每个可刷新区域使用固定容器，状态变化不推动周围布局。状态组件包括：骨架加载、空状态、内联错误、重试按钮和提交结果 Toast。关键删除和积分操作使用带明确对象名称的确认框。

### 15.2 请求行为

1. 页面初始化请求可以并行，但同一资源的重复刷新会取消旧请求。
2. 写按钮提交后进入忙碌状态并保持尺寸不变。
3. 401 保存当前地址并进入登录页。
4. 403 区分 CSRF 失效与权限不足；CSRF 失效允许刷新令牌后安全重试一次。
5. 409 展示服务端最新状态并刷新对应区域。
6. 网络错误不清空用户尚未提交的表单内容。

### 15.3 移动端

相册和商品使用稳定网格；弹窗高度受视口限制；底部操作避开安全区；上传选择和进度适合单手操作；时间线在窄屏改为单列。触控设备不显示只有悬停才能看到的关键操作。

## 16. 日志、健康检查与恢复

### 16.1 日志结构

每行 JSON 日志至少包含：时间、级别、事件、请求 ID、用户 ID 的不可逆摘要、接口、结果和安全清理后的上下文。日志按大小轮换并保留固定数量。

### 16.2 健康检查

`api/ping.php` 对已登录用户可返回 `success`、服务器时间和数据层是否可读写。详细检查只通过 `php scripts/doctor.php` 输出，包括 PHP 版本、扩展、配置、权限、数据校验、上传保护和备份状态。

### 16.3 备份

备份脚本先取得全局只读维护锁，再复制 `data/` 中的有效业务数据和 `uploads/`。备份包包含文件清单、大小和 SHA-256 校验值，不包含缓存、日志、临时文件和锁文件。

### 16.4 恢复

恢复脚本默认只预览。正式恢复前验证清单与校验值，创建当前状态快照，然后替换数据。恢复失败自动回到恢复前快照。恢复后运行配置和数据完整性检查。

## 18. 部署文件与文档

### 18.1 Web 服务器

Apache 保留 `.htaccess` 保护，并在 README 说明必须允许对应目录规则生效。Nginx 提供等价配置示例，明确拒绝访问 `data/`、私密上传、备份、日志、点文件和 PHP 以外的脚本入口。

### 18.2 PHP

部署文档要求 PHP 8.2 以上，并列出 `json`、`mbstring`、`fileinfo`、`gd` 和可选 `curl`。建议设置上传大小、POST 大小、内存、执行时间、会话 Cookie 和错误日志位置。

### 18.3 权限

代码文件由部署用户拥有并只读给 Web 进程；`data/` 与 `uploads/` 仅授予必要写权限。文档使用用户组和 `750/770` 一类示例，不再使用全员可写权限。

### 18.4 更新步骤

1. 运行 `doctor.php` 并确认当前状态正常。
2. 创建完整备份。
3. 进入短暂维护状态，阻止新写入。
4. 更新代码，保留实际配置、数据和上传目录。
5. 执行必要的数据格式迁移。
6. 再次运行检查和冒烟测试。
7. 退出维护状态；失败则回退代码并恢复快照。

## 21. 实施边界

本设计不要求先重写为框架项目，也不要求先迁移数据库。只有当现有 JSON 文件经过锁、校验、事务和备份改造后仍无法满足实际稳定性，才单独提出存储迁移方案。

当前版本的优先级始终是：数据正确高于新功能，安全边界高于视觉变化，核心流程高于装饰效果，真实部署验证高于本地演示。
